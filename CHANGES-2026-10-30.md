# CMI Group repository changes - 30 October 2026

This note records the block/brick estimator work completed in this repository
today, the GitHub push issue reported during setup, and practical improvements
for developing and releasing the feature.

## Changes made

### Wall quantity estimator

- Added [`block-estimator.html`](./block-estimator.html) as a standalone
  estimator page. The home page links to it, and the construction and
  construction-material supply cards on [`services.html`](./services.html)
  link to it as well.
- Added [`assets/js/block-estimator.js`](./assets/js/block-estimator.js) to
  let a visitor enter multiple wall sections and optional door, window, or
  other openings. Wall and opening dimensions are entered in metres; masonry
  unit dimensions and mortar joint width are entered in millimetres.
- The estimate subtracts opening areas from total wall area, divides the
  resulting net area by the unit face area including the mortar joint, applies
  the selected waste percentage, and rounds the final unit count up.
- Results show the wall measurements, opening deductions, selected unit size,
  joint width, joint-adjusted face area, base quantity, waste quantity, final
  count, and calculation formula. Input checks cover missing or invalid values,
  excessive waste, incomplete opening records, and opening area greater than
  the wall area.
- Added [`assets/css/block-estimator.css`](./assets/css/block-estimator.css)
  for responsive layout and result presentation.
- The estimator is explicitly a preliminary masonry-unit quantity tool. It
  does not estimate cement, sand, mortar quantities, or prices, and is not
  presented as a quotation or full bill of quantities.

### Quote-request handoff

- The estimator's quote-request action stores the last successful estimate
  summary in session storage and opens the existing contact form.
- Added [`assets/js/contact-estimate-prefill.js`](./assets/js/contact-estimate-prefill.js)
  to prefill the contact message with the calculated quantity, assumptions,
  wall and opening measurements, and disclaimer. Visitors can edit the
  message and add their contact details before submitting.
- Updated [`contact.html`](./contact.html) with the form anchor, prefill
  status, and a 5,000-character message limit.
- Updated [`functions/api/contact.js`](./functions/api/contact.js) so the
  server accepts messages up to 5,000 characters while retaining the existing
  1,000-character limit for other contact fields. The endpoint still validates
  the submitted fields and sends the message through the existing email helper.

## Verification performed

The page and calculator were exercised in the integrated browser:

- A 5 m by 3 m wall with a 0.9 m by 2 m opening produced a 13.2 m² net wall
  area and an estimate of 161 concrete blocks using the displayed defaults.
- A two-wall example calculated a combined estimate.
- A waste allowance above the 25% maximum displayed a validation error.
- A two-wall estimate was carried into the contact form with both wall
  measurements, the quantity, and the preliminary-estimate disclaimer.

These are manual browser checks, not a replacement for automated tests or a
live delivery test through Cloudflare Pages and Resend.

The configured remote is

Changing `git push` to `git push --set-upstream` cannot fix a missing repository
or insufficient access. The URL was confirmed, but the repository's existence
and push permissions still need to be verified in GitHub.

Before attempting the first site push:

1. Sign in to GitHub and confirm the repository exists under the intended owner
   and that the current account has write access.
2. Verify connectivity with `git ls-remote origin`.
3. Inspect the worktree and staged file list. Add the intended site files, but
   exclude secrets, local credentials, generated files, and unrelated content.
4. Save the README as UTF-8 and give it useful project setup and deployment
   instructions before committing it.
5. Commit the reviewed files, then push `main` with upstream tracking.

Do not delete a `.git\config.lock` file while a Git operation may still be
running. If the lock warning recurs, first close other Git clients and verify
that no Git process is active; remove only that specific stale lock if it
remains.

## How to improve this work

### 1. Confirm construction assumptions with CMI

The current form defaults to a 400 mm by 200 mm unit, a 10 mm mortar joint, and
a 5% waste allowance. These are editable examples, not a verified CMI
specification. Before using the estimator for procurement, have CMI's
construction professional confirm:

- which block and brick types and nominal sizes to offer;
- what joint width and waste allowances are suitable for those materials;
- how to treat wall corners, intersections, bonded returns, partial units, and
  openings near wall edges; and
- whether different wall types need separate estimates.

Keep cement, sand, mortar quantities, and prices excluded until CMI approves
the mix assumptions, local package/supply units, and current prices. If those
are later added, present them as separately reviewed estimates with their
assumptions and effective date.

### 2. Separate and test the calculation logic

The estimator currently builds the interface and performs validation and
calculation in one browser script. A stronger next step is to move the
calculation into a small, pure function that receives validated wall and unit
data and returns net area, face area, base quantity, waste, and final quantity.
Keep DOM updates and quote-message formatting in the page script.

Add automated tests for at least:

- a wall with no openings;
- one or multiple openings;
- multiple walls;
- zero waste and non-default unit dimensions;
- a result that must round up;
- empty, negative, non-finite, and incomplete input;
- openings that exceed the wall area; and
- waste at and beyond the allowed limit.

Also consider validating the physical placement of openings, not just their
combined area. The current area check cannot determine whether two openings
overlap or whether their locations fit within a wall.

### 3. Make the quote handoff robust

Continue generating the quote summary from the same validated calculation
result shown to the visitor, rather than recalculating it separately. Keep the
summary editable, limit its size in both browser and server validation, and
show a clear recovery action if browser storage is unavailable. Test the handoff
on the deployed domain, including the actual contact submission and delivery
to CMI's inbox.

### 4. Add repeatable checks before deploying

There is no project-level automated test command documented here. Add a
lightweight test setup that matches the site's static HTML and Cloudflare Pages
Functions, and run it before publishing. A practical release check should
include:

- JavaScript syntax and estimator calculation tests;
- checks that links and required form elements exist;
- browser tests at desktop and mobile widths;
- a local Pages preview that exercises `/api/contact`; and
- a staging submission confirming that Cloudflare and Resend deliver the
  estimate request successfully.

Do not treat a successful local `file:` browser test as proof that the deployed
API, email settings, or production links are configured correctly.

### 5. Improve repository readiness

Before sharing the site through GitHub, add a meaningful UTF-8 `README.md`
covering the project, local preview instructions, Cloudflare Pages setup,
required environment variables, and deployment/testing steps. Add a reviewed
`.gitignore` for local tools and secrets. Stage and inspect changes in small,
coherent commits, and confirm the first commit includes the intended website
files before pushing.
